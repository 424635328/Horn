# 文档骨架

骨架是参照，不是目录。短文只留三五个模块；体系化文档再全开。

## 1. 通用骨架

````markdown
# 标题：一句话说清产物是什么

> 摘要：读者是谁、读完能做什么、不解决什么。三行以内。

## 前置条件

（版本、权限、依赖、需要先掌握的概念。没有就写"无"。）

## 核心结论

（3~5 条判断，每条带一句理由。方案类必写，教程类可省。）

## 1. 主体章节

（每节开头 1~3 句给结论，再展开。）

### 1.1 子问题

## 2. 边界与常见问题

（什么情况下不适用；与相近方案的区别；常见误用。）

## 附：变更记录（可选）

| 日期 | 版本 | 变更 |
|---|---|---|
````

外层用四个反引号，因为骨架里可能再嵌代码块。

## 2. 三种常见变体

| 类型 | 必含 | 可省略 | 顺序 |
|---|---|---|---|
| 方案设计 | 背景与目标、方案对比、决策与理由、风险与回滚 | 逐步操作 | 问题 → 备选 → 结论 → 代价 |
| 操作指南 | 前置条件、步骤、验证、排错 | 原理推导 | 目标 → 步骤 → 验证 → 排错 |
| 复盘 | 时间线、根因、处置、改进项 | 完整推导 | 事实 → 根因 → 措施 |

## 3. 每节的完成判据

| 模块 | 完成判据 |
|---|---|
| 摘要 | 三行内说清"给谁、能做什么、不解决什么" |
| 前置条件 | 缺任何一条都会导致读者卡住，且已写出版本或权限 |
| 核心结论 | 每条能被单独引用，且带条件 |
| 主体章节 | 只读每节开头三句，能复述全文主线 |
| 示例 | 代码、输入、输出、正文结论四者一致 |
| 边界 | 至少一条"不适用"与一条"看起来像但不是" |
| 变更记录 | 只记事实，不记意图 |

## 4. 迷你范例

下面是一段可直接模仿的片段，展示摘要、结论、表格、代码块与提示块的配合。

````markdown
# 给 CLI 加一个可机读的校验步骤

> 读者：维护内部工具链的工程师。读完能把"人工检查"换成一条返回退出码的命令。不涉及 CI 配置。

## 核心结论

- 校验的价值在于**退出码**，不在于输出好看。
- 规则只写一份：调用方复制规则，迟早会出现两套结论。

## 步骤

| 步骤 | 动作 | 验证 |
|---|---|---|
| 1 | 写检查函数 | 单测覆盖正控与负控 |
| 2 | 接 CLI | `--help` 退出码 0 |
| 3 | 接入提交钩子 | 违规样本被拦住 |

```bash
node tools/check.mjs --path ./doc.md
echo $?   # 0 通过，4 失败
```

> ⚠️ **避坑提示：** 只判断"输出里有没有 ERROR"会漏掉进程崩溃；必须同时看退出码。
````

注意范例里的细节：摘要三行说清边界；结论带条件；表格列数一致；代码块标了语言；提示块只讲一个具体陷阱。

## 5. 交付前替换清单

- 所有占位符（【】、TODO、待补充）已替换为真实内容。
- 表格示例数据与正文结论一致。
- 代码块标注语言，能按文中步骤跑通。
- 相对链接指向的文件真实存在。
- 没有残留"本文档将介绍""综上所述"这类模板句。
