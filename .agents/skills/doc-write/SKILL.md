# 通用文档写作

一份好文档要同时过三关：**读得懂**（结构与直觉）、**用得上**（步骤与边界）、**信得过**（事实与证据）。三者冲突时，先保准确，再保可读，最后才是篇幅。

分工：应试讲解、学习型长文属于另一支写作 skill（未随本仓库分发）；本 skill 面向交付型文档——方案、教程、复盘、README、对外说明。

## 一、开工前：六个参数，缺省即用默认

除主题外不要为次要参数中断任务。唯一例外：主题本身无法确定。

| 参数 | 缺省值 |
|---|---|
| 读者 | 有该领域入门基础、需要照着做或做判断的人 |
| 目的 | 让读者读完能完成一件事，或能做出一个判断 |
| 类型 | 按内容判断：教程 / 操作指南 / 参考 / 解释（见第二章） |
| 长度 | 由信息密度决定，不设字数目标 |
| 平台 | 通用 Markdown（GitHub 风格）；语雀等平台按第五章处理 |
| 术语 | 简体中文；首次出现给英文全称或原文 |

## 二、先定类型：四类文档对应四种结构

| 类型 | 读者的问题 | 主体结构 | 常见错误 |
|---|---|---|---|
| 教程（tutorial） | "带我走一遍" | 线性步骤 + 每步可验证的结果 | 讲原理打断操作节奏 |
| 操作指南（how-to） | "这件事怎么做" | 按目标分节，每节给步骤与排错 | 写成教程，从头教起 |
| 参考（reference） | "这个参数是什么" | 按条目组织，字段齐全、可跳读 | 夹带教学与主观建议 |
| 解释（explanation） | "为什么这样设计" | 从问题到机制再到权衡 | 堆术语、不给反例 |

一篇文档只以一种类型为主。混写时，把次要类型降级为附录，并在开头说明"想动手直接看第 X 节"。

这个四分法常被称作 Diátaxis（Daniele Procida 提出），本文件只借用其分类思想，不照搬其网站措辞。

## 三、工作流（内部执行，不输出过程）

每步的**完成判据**不满足，不要进入下一步。

1. **定契约** —— 一句话写出"读者是谁、读完能做什么、不解决什么"。
   判据：这句话里的每个词都能被验证（"能做什么"是动作，不是"了解"）。
2. **列大纲** —— 每个一级标题配一句中心结论，按"是什么 → 为什么 → 怎么做 → 边界"排序。
   判据：只看标题能复述全文主线。
3. **写主体** —— 每节按需覆盖：定义、解决的问题、直觉、机制、边界；细则见 [WRITING-SPEC.md](references/WRITING-SPEC.md)。
   判据：每个抽象概念都有可画出的解释，并指出不适用的场景。
4. **排版** —— 按目标平台套标题、表格、代码块、公式；平台差异见 [PLATFORMS.md](references/PLATFORMS.md)。
   判据：全文不含该平台渲染不了的写法。
5. **机器校验** —— 落盘后跑检查器，要求 0 error。
   判据：退出码 0；warn 逐条判断是真问题还是可接受。
6. **自检** —— 八项（结构 / 覆盖 / 逻辑 / 准确 / 实用 / 排版 / 可维护 / 冗余），清单见 WRITING-SPEC。
   判据：任一项不过就改，改完重跑第 5 步。

## 四、硬性要求

1. **先问题后定义**：先说解决什么痛点，再给严谨定义，不要开篇堆定义。
2. **结论先行**：每节开头 1~3 句给结论或总览，再展开。
3. **比较用表、流程用图**：多方案对比用表格；执行顺序、状态转换用 Mermaid。图表只在比文字更有解释力时出现。
4. **公式必须解释**：含义、符号、关键推导、成立条件、使用边界。
5. **示例自洽**：代码、数据、结论三者对齐；能跑的要标语言、依赖与验证方式；伪代码必须标明。
6. **不编造**：API、命令、数据、版本行为都要可核实；无法核验就写明核验边界。
7. **区分事实与判断**：客观事实、普遍实践、经验建议、个人判断不混说；不把常见做法说成唯一解。
8. **术语一致**：同一概念全文一个叫法，首次出现给中英对照。
9. **提示块要有增量**：💡 核心观点、⚠️ 避坑、✅ 推荐、ℹ️ 补充，只在提供正文之外的判断时用。
10. **不写空话**：删掉"众所周知""显而易见""综上所述"，删掉删了也不损失理解的段落。

## 五、平台适配

| 目标平台 | 做法 |
|---|---|
| 通用 Markdown（GitHub / GitLab / Obsidian） | 按本文件即可；`<details>`、脚注可用 |
| 语雀 | 读 [PLATFORMS.md](references/PLATFORMS.md) 的语雀一节，并用 `--profile yuque` 校验 |
| 飞书 / Notion / 其他 | 未验证其 Markdown 兼容性；按通用写法产出，交付前在目标平台抽查表格与代码块 |
| Word / PDF | 交给外部 docx 工具（未随本仓库分发），本 skill 只负责内容 |

平台差异集中在三处：公式分隔符、折叠块、Mermaid 语法。其余结构规则通用。

## 六、机器校验

```bash
node .agents/skills/doc-write/scripts/check-doc.mjs \
  --path ./doc.md --profile generic --json ./doc.check.json
```

路径相对仓库根目录解析（`.agents/skills/` 已随仓库分发）。

- `--profile generic`：标题层级、表格列数、代码块语言、相对链接、占位符、分割线空行。
- `--profile yuque`：追加公式分隔符、`<details>`、`$$` 配对、Mermaid 子图与双向箭头。
- 退出码：`0` 通过 / `2` 参数或路径问题 / `3` 内部错误 / `4` 有 error。`--strict` 让 warn 也失败。

改检查器后先跑它自己的回归：`node --test ".agents/skills/doc-write/tests/*.test.mjs"`。

## 七、交付纪律

- **只输出文档本体**：不输出写作计划、分析过程或"以下是为你整理的文档"这类开场。
- 正文从一级标题 `#` 开始，读者全选即可粘贴或提交。
- 需要存盘时写成 `.md`，先跑校验再交付；直接贴在对话里的文档同样要过校验。
- 没有把握的事实写明核验边界，不要用推测填充。
